Governed Evolving Memory · research build

When a fact changes, GEM fixes what was built on it.

Agent memory stores facts, and facts get derived from other facts. When one changes, ordinary memory updates that one fact. Everything worked out from it stays in memory as true. GEM records what depends on what, follows those links when something changes, and marks each dependent fact as updated, stale, or unaffected.

How it works

Two passes on every write, and a cascade when something changed

A new fact is first compared with the facts most similar to it (does it change any of them?), then linked to the facts it was derived from. If it changed something, GEM walks the derived-from links and re-checks each dependent against that specific change.

What you get

An MCP server, a Python library, and tool definitions

The tool surface matches common agent-memory servers (save, forget, search, list, memory spaces). The difference is in what comes back: every write reports the facts it changed further down, and search keeps outdated matches in a separate list instead of mixing them in.

MCP server

For Claude Code, Claude Desktop, Cursor and other MCP clients. Runs locally over stdio.

pip install -e ".[mcp,embeddings,jev]"
claude mcp add gem -- python -m gem.mcp_server

Python library

Pin dependencies where they matter; let GEM infer the rest.

from gem import Memory
m = Memory()
home = m.add("I live in Bangalore").id
m.add("My commute is 45 minutes",
      derived_from=[home])
r = m.add("I moved to Mumbai")
r.invalidated   # [commute → STALE]

Where it fits

Built for memory where facts depend on each other

GEM is a targeted layer, not a general replacement. When facts are independent, flat memory is as accurate and cheaper.

01 · engineering teams

Requirements and change impact

Traceability tools mark everything linked to a changed requirement as "suspect", and teams wade through false alarms. GEM flags only items whose specific dependency changed, with why as the review trail.

02 · coding agents

Project memory that doesn't rot

Agents act on confident project notes without re-checking them. When a design decision changes, GEM tells the agent which conventions, limits and workarounds were built on it. See the runtime migration example above.

03 · personal & multi-agent

Assistants and shared plans

A move, a new manager, a slipped date: the routines and plans built on them get updated or flagged, and several agents can share one memory space.

Use GEM when

  • agents act on facts derived from other facts
  • a fact read as true when it's outdated is costly (ops, compliance, tool calls)
  • reads outnumber writes, so the cascade cost is paid once

Skip it when

  • facts are flat and independent (preferences, profile fields)
  • memory is write-heavy and rarely read
  • a wrong-but-cheap answer is acceptable
