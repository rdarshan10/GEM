    GEM · memory for AI agents

    Change one fact. GEM fixes what depended on it.

    Agent memory that keeps track of which facts were worked out from which. When one changes, GEM rewrites what it can, flags what it can't, and leaves the rest alone.

    See how it works ↓Add it to your agent

    MCP server + Python library · bring your own model

    01 · the problem

    Memories depend on other memories.

    Your commute was worked out from where you live. Your alarm, from the commute. The coffee maker, from the alarm. GEM records each of these dependencies as it stores a fact, whether you give it or GEM infers it.

    02 · the problem

    Then one changes.

    “I moved to Mumbai.” Before storing it, GEM compares it with similar facts. One conflicts directly, where you live, and is updated.

    03 · the problem

    Ordinary memory stops there.

    Same write, flat memory. The direct conflict is fixed. The four facts built on it are still served as true, and nothing marks them wrong. This is what your agent reads back:

    search_memory("how long is my commute?")
    resultsMy commute to the office is 45 minutes

    04 · how GEM works

    GEM follows the links.

    The change runs down every derived-from link, and each fact is checked against this change. Commute, alarm, coffee maker and rent go stale. Your timezone is unaffected: Mumbai is still IST, so the cascade stops there.

    05 · how GEM works

    When the new value follows, it's rewritten.

    A different memory: your manager changes from Alice to Bob. Here every new value can be worked out from the change, so each routine built on it is rewritten. Bob gets the weekly report, approves time off, and writes your review.

    06 · how GEM works

    When it doesn't, it's flagged, not guessed.

    Nothing in “I moved to Mumbai” says how long the new commute is, so GEM doesn't invent one. The fact is marked stale and handed to your agent, which asks you:

    search_memory("how long is my commute?")
    resultsonly facts that are still true
    staleMy commute to the office is 45 minutes → ask the user

    Stale facts also come back in each write's result and from get_stale. Your answer is saved as a new fact.

    07 · how GEM works

    Most decisions are cheap.

    Each hop is one batched question to a small decision model that answers with probabilities: the rings. The LLM only writes corrections and settles doubts. Stopping the cascade takes 90% confidence; anything doubtful goes to the LLM.

    Where it matters.

    GEM pays off wherever an agent acts on facts that were worked out from other facts. Each example runs in the playground.

    • 1

      Coding agentsProject memory that doesn't rot.

      A platform decision changes. The limits, budgets and workarounds built on it never mention the platform, so text search can't find them. GEM reaches them through the links.

    • 2

      Personal assistantsLife changes, routines follow.

      A move, a new manager. Routines are rewritten when the new value is known and flagged for you when it isn't, so the assistant never plans around the old life.

    • 3

      Planning & operationsPlans made of dependencies.

      Dates set relative to other dates, budgets that depend on two facts at once. One change reaches everything downstream and nothing beside it.

    • 4

      Change impactPrecision instead of alarms.

      Only what depends on the changed property is touched; a neighbouring dependency tree is left alone. Fewer false alarms than marking everything linked as suspect.

    Add it to your agent.

    Run GEM as an MCP server for Claude Code, Claude Desktop, Cursor and other clients, or import it as a Python library.

    MCP SERVER
    git clone https://github.com/rdarshan10/GEM && cd GEM
pip install -e ".[mcp,embeddings]"
cp .env.example .env        # pick your model here
claude mcp add gem -- python -m gem.mcp_server
    PYTHON
    from gem import Memory

m = Memory()
home = m.add("I live in Bangalore").id
m.add("My commute is 45 minutes", derived_from=[home])

r = m.add("I moved to Mumbai")
r.invalidated   # [My commute is 45 minutes]
    • add_memorySave or forget a fact. Returns what it updated and what it made stale, several links away.
    • search_memoryValid matches, with outdated ones in a separate list.
    • get_profileA summary built only from facts that are still true.
    • get_staleFacts to reconfirm with the user.
    • whyThe facts a fact was derived from.
    • list_memoriesEverything in a memory space.

    Bring your own model. Ollama (local or cloud) and Groq are built in and chosen in .env. Any other provider takes one small class in gem/llm.py with two methods. An optional decision layer cuts LLM calls further (architecture). Memory is saved as JSON files by default, or in FalkorDB.

    Honest about the edges.

    What GEM isn't for, and what it can't do yet.

    Built for chains

    If your facts are independent, such as preferences and profile fields, flat memory is as accurate and cheaper.

    Inferred links miss some

    When you don't pass derived_from, GEM infers links with about 85–88% recall in our tests. Pin the ones you can't afford to miss.

    Stale facts wait for an answer

    When a new value can't be worked out, GEM flags the fact instead of guessing. Someone still has to answer.
